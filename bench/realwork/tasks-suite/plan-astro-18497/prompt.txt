A bug report came in for this repository:

Title: Server island: uncaught TypeError when the island fetch fails

### Astro Info

```block
Astro                    v7.4.2
Vite                     v8.3.5
Node                     v24.16.0
System                   macOS (arm64)
Package Manager          pnpm
Output                   static
Adapter                  @astrojs/node (v11.1.9)
Integrations             none
```

### If this issue only occurs in one browser, which browser is a problem?

All browsers. Chrome logs `Uncaught (in promise) TypeError: Failed to fetch`, Safari logs `TypeError: Load failed`.

### Describe the Bug

The inline script that loads a `server:defer` island does this (`packages/astro/src/runtime/server/render/server-islands.ts`, `getIslandContent`):

```js
let response = await fetch('/_server-islands/Island?e=…&p=…&s=', { headers });
replaceServerIsland('…', response);
```

If the response is not 200 or not `text/html`, `replaceServerIsland` returns and the fallback stays. But if `fetch()` itself rejects there is no catch. The top-level await rejects and the browser reports an uncaught TypeError. The fallback still stays, so the page looks fine, but every such page load logs an error and error trackers pick it up. The script is generated, so I can't wrap it in app code.

This happens whenever the island request doesn't complete: the user leaves the page while it's in flight, the connection drops on mobile, or the request gets redirected to another origin without CORS headers. I got the last one from a crawler that rendered my page under the apex domain, which redirects to www. In my Sentry these show up as `TypeError: Failed to fetch` and `TypeError: Load failed` with the inline island script as the only frame.

#16341 fixed the same problem for `astro-island` hydration: import failures are caught and an `astro:hydration-error` event is dispatched. The server island script didn't get the same treatment.

### What's the expected result?

A failed fetch should behave like a non-200 response: keep the fallback, don't throw. The #16341 approach would be ideal, a cancelable event like `astro:server-island-error` so apps can react, with a console error only if nobody cancels it. The minimal fix:

```js
let response;
try {
  response = await fetch('…', { headers });
} catch {
  return;
}
replaceServerIsland('…', response);
```

`await r.text()` in `replaceServerIsland` can fail the same way and could use the same guard.

### Link to Minimal Reproducible Example

https://github.com/cinemanja/astro-server-island-fetch-repro (StackBlitz: https://stackblitz.com/github/cinemanja/astro-server-island-fetch-repro)

One page with one `server:defer` island and a fallback, Node adapter, Astro 7.4.2.

1. `pnpm install && pnpm dev`
2. Open `http://localhost:4321/?offline`. The page stubs `fetch` to reject `/_server-islands/` requests. The fallback stays and the console shows `Uncaught (in promise) TypeError: Failed to fetch`.
3. Or open `http://localhost:4321/`, block `_server-islands` in DevTools (Network, request blocking) and reload. Same result.

Without `?offline` the island renders fine with no errors.
