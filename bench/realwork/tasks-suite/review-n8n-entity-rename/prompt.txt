Title: refactor(core): Move the agent file entity and repository into the knowledge module

Description:
## Summary

The knowledge module (`packages/cli/src/modules/knowledge`) is the new home of agent knowledge. Code moves there from the agents module in steps, with no user-facing change.

This PR moves the uploaded-file entity and its repository: `AgentFile` becomes `KnowledgeFile`, still mapped to the `agent_files` table, and `AgentFileRepository` becomes `KnowledgeFileRepository`, with its method names unchanged. The entity no longer declares the relation to `Agent`; it keeps the `agentId` column and both indexes. The knowledge module registers the entity, and the agents module stops doing so. No migration: the table, its foreign key and its cascade are untouched.

Two commits for review: the first is `git mv` plus import fixes, the second is the renames, the dropped relation and the one decision below.

## Why

The knowledge module must not depend on agent internals, and the agents module must not own the knowledge tables. Dropping the TypeORM relation removes the last import of the agents module from the entity. The database foreign key from `CreateAgentFilesTable` still cascades the rows with the agent; a new integration test covers that, because the entity no longer expresses it.

With `N8N_DISABLED_MODULES=knowledge` the entity is now not registered, so every path that reads the repository needs a module guard. The guards from the scaffold PR cover the routes, the facade and runtime reconstruction; #43087 covers the telemetry reads. The remaining path is the file cleanup on agent and project deletion. It now logs a warning and returns when the module is off: the rows go with the agent through the database cascade, but their stored bytes stay. This is an accepted gap, documented in the module `AGENTS.md`. The alternative, a cleanup that reads the table without entity metadata, is not a pure move and can follow if operators need it.
