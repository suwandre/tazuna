I've fixed the bug. Here's a summary.

## Root cause

`refactoring.FindImportStatements` (called from `Context.findImportTargets`) collected import blocks into an `addrs.Map[addrs.ConfigResource, ImportStatement]`. `ConfigResource` identifies a *resource* (mode/type/name), not an *instance* — it has no instance key (`["a"]`, `[0]`). So multiple import blocks targeting different instances of the same `for_each`/`count` resource all keyed to the same entry, and `Put` silently overwrote all but the first. That matches the report exactly: only the first block per resource survived, single-instance resources were unaffected, and order (not key) determined the winner.

## Fix

Changed `FindImportStatements` to return `[]ImportStatement` and dedupe with an explicit `seen` key set:

- When an import block's `to` expression can be statically resolved (`hcl.AbsTraversalForExpr` + `ParseAbsResourceInstance`), the key is the full **resource instance** address, so distinct instances of an expanded resource are all retained.
- Otherwise (dynamic `for_each` on the import block, unknown index) it falls back to the resource-level `ConfigResource`, preserving prior behavior.
- The `seen` set is threaded through recursive module traversal, preserving the existing "parent module overrides child module" semantics.

The caller `context_plan.go` was updated from `.Values()` iteration to a plain slice.
