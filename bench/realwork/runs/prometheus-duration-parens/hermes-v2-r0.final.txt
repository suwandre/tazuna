Parentheses around a plain duration literal now survive `Expr.String()`. `go test ./promql/... ./web/... ./rules/... ./cmd/promtool/... ./util/...` passes. I didn't run `make lint` or the full `make test`.

With `ExperimentalDurationExpr` on, the cases from the issue now print like this:

| Input | `String()` |
|---|---|
| `foo offset (5)` | `foo offset (5)` |
| `foo offset -(5)` | `foo offset -(5)` |
| `foo offset +(5)` | `foo offset (5)` |
| `foo offset (5m)` | `foo offset (5m)` |
| `foo[(5s)]` | `foo[(5s)]` |

`+(5)` drops the plus, as `+(5*2)` already does.

**Fix:** `*NumberLiteral` has nowhere to record parens, so a parenthesised literal in a duration position is now wrapped in a unary-plus `*DurationExpr{Wrapped: true}`. That goes through `paren_duration_expr` and `applyUnaryOpToDurationExpr` (`generated_parser.y`, `parse.go`). I regenerated `generated_parser.y.go` with goyacc, and the shift/reduce and reduce/reduce conflict counts are unchanged.

**AST change:** a parenthesised literal now fills `OriginalOffsetExpr`, `RangeExpr` or `StepExpr`. `OriginalOffset`, `Range` and `Step` are still filled at parse time. `foo[(0s)]` is still rejected at parse time, and the engine's duration evaluator already handles the wrapped literal.

**Related changes:**
- `Pretty()` for a unary plus no longer prints the `+`, so it matches `String()` (`prettier.go`).
- Subquery step printing now prefers `StepExpr` over `Step` (`printer.go`). Without that, `foo[(5s):(1s)]` came out as `foo[(5s):1s]`.

**Tests:** I added printer round-trip cases (`printer_test.go`) and parse tests for `foo[(5s)]` and `foo[(0s)]`. I also updated the expected AST for `foo offset +(5)` and `foo offset -(5)` in `parse_test.go`, since they now carry the wrapped expression.
