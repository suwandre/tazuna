Ask: preserve parentheses around a plain duration literal on `Expr.String()` round-trip - wanted: the five lossy cases from the issue round-trip, with tests.
For you: fixed. `go test ./promql/... ./web/api/...` passes, and so does `./cmd/promtool/...` from an earlier run. `gofmt` and `go vet` on `promql/parser` are clean.

**Cause:** for a bare `(5)` the offset and range rules only keep the number. They convert it into `OriginalOffset` or `Range` and drop the expression, so the parens are gone.

**Fix:**
- A parenthesised plain literal in a duration position is now kept as a `*DurationExpr` with `Op: ADD`, `Wrapped: true` and the literal as `RHS`. The engine already evaluates a unary-plus `DurationExpr`, so evaluation is unchanged.
- This covers `(N)`, `+(N)` and `-(N)`. `-(5)` becomes a `SUB` node around the wrapped literal, the same shape `-(5m + 1m)` already has.
- The changes are in `promql/parser/parse.go` and the `paren_duration_expr` rule in `generated_parser.y`, with `generated_parser.y.go` regenerated by `goyacc`.
- In `prettier.go`, a unary-plus duration now prints without the `+`. `String()` already did this, and the pretty printer would otherwise have shown `(+5s)`.

**Round-trips now:**

| Input | `String()` |
|---|---|
| `foo offset (5)` | `foo offset (5)` |
| `foo offset -(5)` | `foo offset -(5)` |
| `foo offset (5m)` | `foo offset (5m)` |
| `foo[(5s)]` | `foo[(5s)]` |
| `foo[(5s):(1s)]` | `foo[(5s):(1s)]` |

`foo offset +(5)` prints `foo offset (5)`. The unary plus is dropped, as it already is for `+(5*2)`. A bare `5` is not marked as a duration, so `(5)` prints as `(5)` and not the `(5s)` you might expect.

**Side effect:** `foo offset (5)` now has `OriginalOffset == 0` and `OriginalOffsetExpr` set, which is how `foo offset (5m + 1m)` already works. The engine fills in the real value. Anything that reads `OriginalOffset` straight from the parsed AST, without going through the engine, now sees 0 for these inputs.

**Regression caught and fixed:** `foo[1 / (0)]` and `foo[1 % (0)]` used to fail at parse time and would now only fail at evaluation. I added `isZeroDurationLiteral`, so the division-by-zero and modulo-by-zero checks still see through the wrapper. I confirmed the parse errors are back.

**Tests:** I updated the `foo offset +(5)` and `foo offset -(5)` AST expectations in `parse_test.go`. I added the round-trip cases to `TestExprString` in `printer_test.go`.
