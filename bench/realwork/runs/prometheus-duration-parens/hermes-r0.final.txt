Parentheses around a plain duration literal now survive `Expr.String()` for offsets and range brackets. `go test` passes for `./promql/...`, `./web/...` and `./cmd/promtool/...`; I did not run `make lint`.

| Input | `String()` before | `String()` now |
|---|---|---|
| `foo offset (5)` | `foo offset 5s` | `foo offset (5)` |
| `foo offset +(5)` | `foo offset 5s` | `foo offset (5)` |
| `foo offset -(5)` | `foo offset -5s` | `foo offset -(5)` |
| `foo offset (5m)` | `foo offset 5m` | `foo offset (5m)` |
| `foo[(5s)]` | `foo[5s]` | `foo[(5s)]` |

- **How it works:** a parenthesised `*NumberLiteral` is now held in a `*DurationExpr{Op: ADD, RHS: lit, Wrapped: true}` (a unary plus, which already prints without the `+`). The change is in `generated_parser.y` (regenerated with goyacc, small diff in `generated_parser.y.go`) and `parse.go`.
- **AST change:** `foo offset (5)` and `foo[(5s)]` now set `OriginalOffsetExpr` or `RangeExpr`, not `OriginalOffset` or `Range`. The numeric field stays 0 until the duration visitor runs, as it already does for `(5m + 1m)`. A consumer that reads `OriginalOffset` straight off a parsed AST, without that visitor, will see 0 for these queries. I updated the two existing `parse_test.go` cases, `foo offset +(5)` and `foo offset -(5)`, to expect the new AST.
- **Parse errors kept:** `foo[(0)]`, `foo[-(5)]` and `foo[(-5)]` still fail at parse time with "duration must be greater than 0". Without the extra check in `positive_duration_expr` they would only have failed at evaluation. The error position now starts at the paren.
- **Prettier:** `DurationExpr.Pretty` printed a unary `+` that `String()` omits. I made it match, since the new node is a unary plus.
- **Tests:**
  - `parse_test.go`: a `foo[(5s)]` AST case and the two parse-error cases.
  - `printer_test.go`: round-trip cases for offsets, ranges and subquery steps.
  - `durations_test.go`: a check that `rate(metric[(5m)] offset -(5))` evaluates to 5m and -5s and prints back unchanged.
