I've fixed it: parentheses around a plain duration literal now survive `Expr.String()`. Every case in the issue round-trips, and `go test` passes for `./promql/...` (`promql`, `promql/parser` and `promql/promqltest`).

| Input | Before | After |
|---|---|---|
| `foo offset (5)` | `foo offset 5s` | `foo offset (5)` |
| `foo offset +(5)` | `foo offset 5s` | `foo offset (5)` |
| `foo offset -(5)` | `foo offset -5s` | `foo offset -(5)` |
| `foo offset (5m)` | `foo offset 5m` | `foo offset (5m)` |
| `foo[(5s)]` | `foo[5s]` | `foo[(5s)]` |
| `foo[5m:(1m)]` | `foo[5m:1m]` | `foo[5m:(1m)]` |

`+(5)` prints as `(5)` because the printer already drops a unary `+`: an existing test expects `foo offset +(5*2)` → `foo offset (5 * 2)`. Scalar expressions like `(5)` and `(5) + 1` are unchanged.

## How it works
- **`parse.go`**: when a single number literal is in parentheses inside an offset or range bracket, a new helper `wrapDurationExpr` wraps it in a unary-`+` `*DurationExpr` with `Wrapped: true`. The printer and the engine's duration evaluator already handle that form. Both the plain `(…)` rule and the `-(…)` / `+(…)` path now use this helper.
- **Errors still caught at parse time**: some checks only looked for a bare number literal, so the wrapper would have pushed their errors to query time. A second helper, `durationLiteralValue`, sees through the wrapper and any unary sign. As a result, `foo[(0m)]` and `foo[-(5m)]` still fail with "duration must be greater than 0", and `foo[5s/(0d)]` and `foo[5s%-(0d)]` still fail with division/modulo by zero.
- **Generated parser**: I regenerated `generated_parser.y.go` with goyacc v0.6.0, the version the Makefile pins. The grammar conflict count is the same as before (96 shift/reduce, 345 reduce/reduce), so only action code changed.

## Behaviour change
`foo offset (5)` now ends up in `OriginalOffsetExpr` instead of `OriginalOffset`, and `foo[(5s)]` sets `RangeExpr` instead of `Range`. Multi-term expressions like `(5m + 1m)` already work this way. Code that reads `OriginalOffset` or `Range` straight after parsing will see 0 until the engine fills them in. The query results are the same.

## Tests
- **`parser/parse_test.go`**: updated the expected ASTs for `foo offset +(5)` and `foo offset -(5)`, and added the four parse-error cases above.
- **`parser/printer_test.go`**: added round-trip cases to `TestExprString`, including nested `((5m))` and subqueries.
- **`promqltest/testdata/duration_expression.test`**: added `offset (4)`, `offset +(4s)`, `offset -(4)` and `[(30m)]`, to check they give the same results as the forms without parentheses.

`go vet` is clean. `golangci-lint` only reports gofumpt formatting issues in four files I didn't touch (`bench_test.go`, `engine.go`, `functions.go`, `promql_test.go`).
