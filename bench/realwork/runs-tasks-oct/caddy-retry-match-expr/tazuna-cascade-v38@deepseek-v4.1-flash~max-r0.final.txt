## Root cause

Since #7569, `reverseProxy()` evaluated **any** `lb_retry_match` set containing an expression matcher against every successful upstream response. A request-only expression (e.g. `{http.request.method} == "POST"`) therefore matched all responses, retrying successful requests until the client got a 502.

## Fix

- **`modules/caddyhttp/celmatcher.go`**
  - During `Provision`, record the placeholder names read by the checked CEL AST (`celPlaceholderNames`), handling both the `{placeholder}` shorthand and direct `ph(req, "...")` calls. A name that isn't a string literal is recorded as `""` (unknown until evaluation time).
  - Added `MatchExpression.Placeholders()`, which returns a copy of those names.

- **`modules/caddyhttp/reverseproxy/reverseproxy.go`**
  - Replaced `matcherSetHasExpressionMatcher` with `matcherSetReferencesResponse`, which only treats a set as a response condition if an expression references response data: `http.reverse_proxy.status_code`, `status_text`, `header.*` (prefix), `upstream.latency`, `upstream.latency_ms`, or an unknown/dynamic placeholder name.
  - The post-round-trip retry check now skips all other expression sets, restoring their pre-v2.11.3 request-condition behavior. Escaped placeholders in string literals and lookalike names (e.g. `status_codes`) are correctly ignored.

## Tests added

- `modules/caddyhttp/reverseproxy/retrymatch_response_test.go` — predicate table; request-only expressions (including the reported POST-with-body against two 200 upstreams) no longer retry; shorthand and `ph()` response expressions still do.
