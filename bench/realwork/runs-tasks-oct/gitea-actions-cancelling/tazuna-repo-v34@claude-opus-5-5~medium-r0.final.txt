**Run stuck in "Cancelling"** (`models/actions/run_job.go:820`)
Your reading was right. When a caller is cancelled, its child job with a task goes to `cancelling`, and that already moves the caller and the run to `cancelling`. Then `cancelOneJob` works from an outdated copy of the caller and writes it as `cancelled` straight away. When the runner later acknowledges the cancel, the caller's computed status is already `cancelled`, so nothing gets written. The run status is only refreshed from a top-level caller's change, so it stays `cancelling` forever.

Now, if any direct child of a caller is still `cancelling`, the caller's status is worked out from its children (so it stays `cancelling`) instead of being forced to `cancelled`. Callers are processed deepest first, so this works at any nesting depth. When the runner acknowledges, the last child becomes `cancelled`, which updates each caller up the chain and then the run.

**Force-cancel doesn't release the waiting run** (`services/actions/cancel.go:56`)
When a cancel changes no job (every job was already finished) and only settles the run's own status, nothing checked the concurrency group afterwards. Now, if no job was updated and the run ends up finished, `cancelRun` triggers the check for that run, which starts the runs waiting behind it. With this, force-cancelling a run that is already stuck, like the ones on your production instance, also lets the waiting run start.
