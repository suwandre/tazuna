The verification command now passes: `go test ./plugins/common/snmp/ ./plugins/inputs/snmp/ ./plugins/processors/snmp_lookup/` ran clean three times in a row, and `go vet` and the race detector on the wrapper tests are clean too. The fix itself was already right; both failures came from the tests.

**What was wrong:**

1. **`TestSnmpInitGosmi` crash.** This wasn't caused by the reconnect change. The test also crashes on unmodified HEAD when the repo sits in a directory whose name contains a colon, like this one (`...deepseek-v4.1-flash:max-...`); it passes in a normal temp dir. The test passed an absolute MIB path, and gosmi splits search paths on `:`, so the MIB module couldn't be found. The test also had no logger set, so logging that warning crashed it. I changed the test to use a relative path, as `mib_loader_test.go` already does, and gave it a logger.
2. **Flaky `TestGosnmpWrapperRequestsReconnectClosedConnection`.** The previous model's new wrapper tests used a 5ms timeout, which gosnmp also uses as the UDP connect timeout. On a busy machine connecting could time out ("dial udp … i/o timeout"). I raised it to 100ms in `wrapper_test.go`.

**The fix as it stands** (I reviewed it and left it unchanged):
- **Connection interface:** it gains `Close()`; the gosnmp wrapper and all the test fakes implement it.
- **Wrapper:** it remembers the engine ID, boots and time from the config. `Reconnect()` does nothing if the connection is open. If it was closed, it restores those configured values and clears `ContextEngineID`, so SNMPv3 engine discovery starts fresh, then connects again. That also looks up the agent's address again. `Get` and `Walk` reconnect first if the connection is closed.
- **`inputs.snmp`:** when gathering the top-level fields or any table fails, it closes that agent's connection. Tests cover both cases recovering on the next gather.

One thing you might trip over: with `-count=3`, `TestFolderLookup` in `plugins/common/snmp` fails on the repeat runs, though it passes on every single run. My guess is that the MIB loader keeps a record of already-loaded paths for the whole process, so repeats behave differently. That isn't touched by this change, but I didn't confirm it fails the same way on HEAD.
